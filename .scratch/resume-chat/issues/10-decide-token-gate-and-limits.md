# Decide token gate, session, and per-token abuse limits

Type: grilling
Status: resolved 2026-09-21
Assigned: clint (claimed 2026-09-21)
Blocked by: 04

## Question

Decide the exact access flow, informed by the Cloudflare token-gating research (ticket 04):

- What the token screen submits and how the server validates it against the per-person token list.
- The session artifact set after a valid token (cookie shape, lifetime, signing).
- Per-token limits: requests per minute, requests per day, output tokens per day — and the failure mode when one is exceeded.
- What an unauthorised or revoked token sees.
- The operating procedure for issuing and revoking a token (where the list lives, who edits it, how fast a revocation takes effect).

HITL.

Two empirical checks to carry in from *Research Cloudflare-native token gating and rate limiting*, settled during implementation rather than blocking this decision: whether the `ratelimit` binding is available on the Workers **Free** plan (no primary doc confirms or denies it), and which expression fields the Free plan permits in WAF custom rules.

The monthly *count* is decided; the daily/minute mechanics stay yours.

## Answer

Resolved 2026-09-21, grilling round (Q1–Q9); all recommendations accepted, confirm round passed.

- **Token list: one varlock secret holding a JSON list of `{id, name, sha256(token)}`** — digest-only storage, per-person entries. Auth stays pure compute, no D1 dependency. Changing the list needs a redeploy; ticket 11 owns the varlock→Workers secret plumbing.
- **Token shape: `rchat_` + 32 random hex chars** (~128 bits, node `crypto.randomBytes`), one per person, generated by a **`npm run token:add <name>`** helper script (handles id + digest bookkeeping; revocation stays a hand edit).
- **Login: `POST /api/login`** with the raw token; server digests it and compares against the list digests (SHA-256 compare, research 04's timing-safe design). On match: session cookie set; on miss: inline "that token didn't work" on the token screen. **No rate limit on login** — 128-bit token space makes brute force impractical.
- **Session: stateless signed cookie** `"<token-id>.<expiry>.<hmac>"` (HMAC-SHA256, signing key in a varlock secret), `httpOnly + secure + sameSite: lax + path: /`, **fixed 7-day maxAge** (no sliding). Every chat request re-verifies HMAC + expiry **and re-checks `token-id` against the current list** — so removing a person from the list kills their existing cookie at their next request: real revocation with zero extra storage.
- **Minute limiter: Workers `ratelimit` binding, 10 requests / 60 s**, keyed by token id; login endpoint exempt. On trip: distinct friendly "you're going too fast — try again in a minute" message. If the binding turns out unavailable on Workers Free (carried empirical check), fallback = D1-based burst check, decided at implementation.
- **Daily cap: 30 requests/token/day.** Monthly 100 turns stands from ticket 09. **No output-tokens-per-day counter**: `max_tokens` 1,000 (ticket 09) already bounds worst case to ~100k output tokens/month ≈ pennies; the turn count is the enforcing unit.
- **D1 counter shape: one table, one row per token per period** — `usage(token_id, day, month, day_count, month_count)` in a single `INSERT … ON CONFLICT DO UPDATE`; daily trip → distinct friendly message, monthly trip → the ticket-09 "monthly question limit" message, minute trip → the "too fast" message.
- **Fail closed on D1 errors**: the counter exists to protect the bill; uncounted turns defeat it. D1 free-tier write ceiling makes a real outage vanishingly unlikely at this scale.
- **Unauthorised / expired / revoked all see the same plain token screen**, message-free — deliberately indistinguishable, leaks nothing about who is on the list.
- **Operating procedure (Clint-only)**: issue = `npm run token:add <name>` → redeploy; revoke = remove the entry + redeploy. **Revocation takes effect at the recipient's next request** (per-request list re-check) — minutes, not seconds, bounded by deploy time. Documented in the README ops section. No admin UI (map Out of scope).

Both carried empirical checks stay with implementation: `ratelimit` binding on Workers Free (with D1 fallback if absent), and Free-plan WAF custom-rule fields (informs only whether a zone-level pre-filter is possible; never load-bearing here).
