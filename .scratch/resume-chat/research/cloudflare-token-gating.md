# Cloudflare-native token gating and rate limiting

**Verdict.** For a Next.js App Router app on Workers (`@opennextjs/cloudflare`), the minimum-complexity design that survives a hostile user is: (1) verify the access token server-side in a route handler by constant-time comparison against a Workers **secret** exposed on `getCloudflareContext().env`; (2) on success set a **stateless HMAC-signed `httpOnly` session cookie** (Web Crypto `crypto.subtle.sign`, verified on every request) so no per-session server state is needed; (3) enforce limits with the **Workers Rate Limiting binding** (free, no storage, GA since Sep 2025, works through the OpenNext adapter because it is just a wrangler-configured binding) for burst control, plus a **D1 daily counter** (one row per token per UTC day, strongly consistent) as a hard spend ceiling. Durable Objects are the strongest (single-object, strongly consistent) counter but add a migration and per-request DO hop; KV is unsuitable as a rate-limit counter (1 write/sec per key, up to 60 s eventual consistency, 1,000 writes/day on the free plan). Zone-level WAF rate-limiting rules on the **Free plan are keyed only by IP** with path-only expressions (1 rule, 10 s period) — they can blunt generic abuse but cannot key on your access token or cookie, so they are a supplement, not the gate.

## (a) Verifying a user-supplied access token server-side

- The app runs as a Cloudflare Worker; route-handler code runs inside it ([OpenNext Cloudflare adapter](https://opennext.js.org/cloudflare)). Bindings, including secrets, are reachable in any route handler via `getCloudflareContext().env` ([OpenNext bindings](https://opennext.js.org/cloudflare/bindings)).
- Store the valid access token(s) as **Workers secrets** (encrypted env values set via `wrangler secret put`; also readable as `process.env` when `nodejs_compat` is on — OpenNext requires `nodejs_compat`) ([Workers Secrets](https://developers.cloudflare.com/workers/configuration/secrets/), [OpenNext get-started: `nodejs_compat` flag](https://opennext.js.org/cloudflare/get-started)).
- Verification itself is plain code in the route handler: read the token from the login POST body (or an `Authorization` header), compare against the secret. Because Workers' standard `crypto.subtle.timingSafeEqual`-equivalent is not in the Web Crypto surface, compare SHA-256 digests of both values (`crypto.subtle.digest`) — constant-time on the digest bytes, using the Workers runtime's full Web Crypto implementation ([Workers Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)). Supporting several tokens (e.g. one per person) means either multiple secrets, one secret holding a JSON list, or a D1/KV allowlist keyed by token hash.
- This gives per-request, server-side verification; nothing about the token is client-trustworthy. The chat endpoint should re-verify the **session** (below) on every request, not trust the page.

## (b) Keeping a session after entry (cookies in an App Router route handler on Workers)

- In App Router, `(await cookies()).set(name, value, options)` is legal **only in a Route Handler or Server Function**, and `httpOnly`, `secure`, `sameSite`, `maxAge`, `path` are all supported cookie options ([Next.js `cookies()` reference](https://nextjs.org/docs/app/api-reference/functions/cookies)). So a `POST /api/login` route handler can verify the token and set the session cookie; `.delete()` / `maxAge: 0` logs out.
- Signing: the Workers runtime implements the **full Web Crypto API** — `crypto.subtle.importKey` + `sign`/`verify` (e.g. HMAC-SHA256) run natively and fast ([Workers Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)). The signing key is a Workers secret ([Workers Secrets](https://developers.cloudflare.com/workers/configuration/secrets/)).
- Recommended cookie: value `"<token-id>.<expiry-unix>.<hmac(token-id, expiry)>"`, attributes `{ httpOnly: true, secure: true, sameSite: "lax", path: "/", maxAge: 60*60*24*7 }` (options table in [Next.js `cookies()`](https://nextjs.org/docs/app/api-reference/functions/cookies)). Stateless verification on each request = decrypt nothing, just re-verify HMAC and expiry; a stolen cookie works until expiry, so a 7-day `maxAge` is the tunable trade-off. `httpOnly` prevents XSS exfiltration from the browser; it cannot help if the user willingly shares their cookie, which is the residual hostile-user risk for any cookie scheme.
- Because OpenNext runs the Next.js server inside one Worker, there is no "session server" — stateless signed cookies (above) or a DB-backed session row are the two options; the signed cookie avoids a KV/D1 lookup per request.

## (c) Cheap per-token limits: KV vs D1 vs Durable Objects

| Store | Free-plan allowance | Pricing (paid) | Consistency / rate-limit fit | Failure mode as a counter |
| --- | --- | --- | --- | --- |
| **Workers KV** | 100k reads/day, **1,000 writes/day**, 1 GB ([KV pricing](https://developers.cloudflare.com/kv/platform/pricing/)); **1 write/sec per key** ([KV limits](https://developers.cloudflare.com/kv/platform/limits/)) | $0.50/M reads, $5.00/M writes ([KV pricing](https://developers.cloudflare.com/kv/platform/pricing/)) | Eventually consistent: "changes may take up to 60 seconds or more to be visible" in other locations; docs explicitly say KV is unsuitable when you need atomic operations and point to Durable Objects instead ([How KV works](https://developers.cloudflare.com/kv/concepts/how-kv-works/)) | Worst fit: burst slips through (stale cached count + write cap), 1,000 free writes/day exhausted by ~1 token's daily traffic |
| **D1** | 5M rows read/day, 100k rows written/day, 5 GB ([D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)) | $0.001/M rows read, $1.00/M rows written ([D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)) | Single primary SQLite → per-statement consistency; 1 row read + 1–2 rows written per `INSERT … ON CONFLICT` counter check (rows billed per row touched, indexed PK lookups stay at 1 row) ([D1 pricing definitions](https://developers.cloudflare.com/d1/platform/pricing/)) | Solid: a burst is counted serially. Failure mode = free-plan daily cap (queries error out when 100k writes/day exceeded) and higher per-request latency than an in-isolate check |
| **Durable Objects (SQLite-backed)** | Available on **Workers Free** (SQLite-backed only): 100k requests/day, 13,000 GB-s duration/day, 5M rows read/day, 100k rows written/day ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)) | $0.15/M requests, $12.50/M GB-s, $0.001/M rows read, $1.00/M rows written ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)) | One object per token = serialized, strongly consistent counter; the canonical Cloudflare answer for rate limiting needing strong consistency ([How KV works, "If you need stronger consistency … consider Durable Objects"](https://developers.cloudflare.com/kv/concepts/how-kv-works/)) | Strongest; cost is one extra DO request per chat request (billed) and an extra deployment artifact (class + migration) |

### Workers Rate Limiting binding — usable from OpenNext? Yes.

- The `ratelimit` binding is GA ([changelog, Sep 19 2025](https://developers.cloudflare.com/changelog/post/2025-09-19-ratelimit-workers-ga/)), configured in the wrangler file as a binding with `simple.limit` and a period of **10 s or 60 s**, invoked as `await env.MY_RATE_LIMITER.limit({ key })` returning `{ success }` ([Rate Limiting docs](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)). No plan restriction is stated in the docs and there is no pricing/billing entry for it ([Rate Limiting docs](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) — no ratelimit section).
- OpenNext apps deploy as a Worker with a wrangler config; bindings declared there are accessible from Next.js server code via `getCloudflareContext().env` ([OpenNext bindings](https://opennext.js.org/cloudflare/bindings)). The wrangler config is created/extended as part of the standard setup ([OpenNext get-started, step 3](https://opennext.js.org/cloudflare/get-started)). Requires Wrangler ≥ 4.36.0 ([Rate Limiting docs](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)); OpenNext itself requires Wrangler ≥ 3.99 ([OpenNext get-started](https://opennext.js.org/cloudflare/get-started)) — use latest wrangler, so both are satisfied. Local dev works via wrangler's binding simulation ([OpenNext bindings, "Local access to bindings"](https://opennext.js.org/cloudflare/bindings)).
- **Failure modes of the binding** (from its docs): counters are **local to each Cloudflare location** — "for each unique key … there is a unique limit per Cloudflare location"; "permissive, eventually consistent, and intentionally designed to not be used as an accurate accounting system" — a burst from one location overshoots slightly because isolates check locally cached counters; it is therefore a *burst* limiter, not an *accounting* system ([Rate Limiting docs, Locality/Accuracy](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)). A determined attacker hitting many locations can multiply their effective limit by the number of PoPs.
- Docs' own best practice: key on a stable user identifier (token/session id), not IP ([Rate Limiting docs, Best practices](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)).

### Zone-level WAF / rate-limiting rules (no app code)

- **Custom rules** (block/challenge by expression): available on Free (5 rules), but **no regex**, and the Free plan limits the rule-expression fields ([Custom rules availability](https://developers.cloudflare.com/waf/custom-rules/)). A "block everything on the chat path unless header X matches" rule is plausible but the Free-plan field surface is narrow and static header values leak in rule config; treat as coarse pre-filter.
- **Rate limiting rules** on Free: **1 rule**, counting characteristic = **IP only**, expression limited to **Path and Verified Bot** fields, counting period = **10 s**, mitigation timeout = 10 s ([Rate limiting rules availability table](https://developers.cloudflare.com/waf/rate-limiting-rules/)). Pro+ unlock host/query/method/header expressions and longer periods; cookie/header/JSON-body counting characteristics require Business+ and Enterprise+ respectively.
- Cloudflare itself warns the zone-level counters lag: "there may be a delay of up to a few seconds between detecting a request and updating rate counters. Due to this delay, excess requests could still reach the origin before Cloudflare enforces a mitigation action" ([Rate limiting rules, Important remarks](https://developers.cloudflare.com/waf/rate-limiting-rules/)).
- Conclusion: zone rules can rate-limit **by IP** on the chat path for free, but cannot enforce **per-token** limits or token possession — they complement, not replace, app-side gating.

## Recommended design (minimum complexity that survives a hostile user)

1. **Token → session**: `POST /api/login` verifies the access token against a Workers secret (digest compare, [Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)); sets a signed, `httpOnly`, `secure`, `sameSite: "lax"` session cookie with 7-day `maxAge` ([Next.js cookies()](https://nextjs.org/docs/app/api-reference/functions/cookies)). No session store.
2. **Per-request auth**: every chat route handler verifies the cookie's HMAC + expiry; rejects otherwise. No network call.
3. **Burst limiter**: `ratelimit` binding, `key` = token id (or session id), `simple: { limit: ~10, period: 60 }`, called before the OpenRouter fetch ([Rate Limiting docs](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/); reachable via `getCloudflareContext().env`, [OpenNext bindings](https://opennext.js.org/cloudflare/bindings)). Free, adds no meaningful latency.
4. **Spend ceiling**: D1 table `usage(token_id, day, requests)` with `INSERT … ON CONFLICT DO UPDATE` returning the new count; refuse at the configured daily cap ([D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) — ~2 rows written + 1 read per chat call, orders of magnitude inside free tier). Strongly consistent, so the ceiling is real even against a multi-location attacker.

Failure modes of this stack: the binding can overshoot slightly per location (by design); D1 adds one query's latency (~tens of ms) and errors if the daily free write cap is hit (fail closed is what you want); cookies can be stolen by their owner — irreducible for any personal-token scheme; the HMAC secret leaking equals total compromise (mitigate: rotate via `wrangler secret put`).

**Total cost: $0** on the Workers Free plan (100k Worker requests/day, KV/D1/DO/binding all within free allowances at personal scale).

## Cheaper-but-weaker alternative

Drop D1 and the DO option entirely: cookie auth + `ratelimit` binding only, with the daily budget enforced only by the binding's 60 s window (e.g. limit 10/60 s ≈ ~14k requests/token/day worst case, more from multiple locations) and/or a Free-plan **WAF rate limiting rule keyed by IP** on the chat path ([availability table](https://developers.cloudflare.com/waf/rate-limiting-rules/)). Nothing to provision beyond one binding in `wrangler.jsonc`. Weaker because: no hard daily spend cap (OpenRouter bill bounded only by per-minute windows × number of locations), IP-keyed WAF punishes shared IPs and misses the token, and zone rule counters can lag several seconds. Reserve for a "trusted friends only" phase; add the D1 ceiling before sharing tokens more widely.

## Open questions

- The Rate Limiting binding docs state no plan restriction and no billing entry; confirmed usable on paid, and community posts imply free-plan availability, but no primary doc sentence says "available on the Workers Free plan" — verify empirically on the free account during prototype (issue 12).
- Exact Free-plan field set for WAF custom-rule expressions (whether `http.request.headers`/`http.cookie` are matchable at all on Free) is not stated on the custom-rules page; the rate-limiting-rules table is explicit (path-only), but if a cookie-conditioned custom rule is desired, confirm in the dashboard before relying on it.
- Session-cookie lifetime vs. token revocation: with stateless signed cookies there is no server-side kill switch; if revocation matters, a small KV/D1 revocation list must be added (not priced into the recommended design).
