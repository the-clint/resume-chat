# Cloudflare deployment path for a Next.js 15+ App Router app

Deploy the app to **Cloudflare Workers** using the **`@opennextjs/cloudflare` adapter** (currently v1.20.x, peer-supporting `next >=15.5.24 <16 || >=16.3.3` [npm registry](https://www.npmjs.com/package/@opennextjs/cloudflare)): it runs App Router route handlers on the Workers runtime with `nodejs_compat` enabled, configures env vars/secrets via the Wrangler config plus `wrangler secret put`, serves the site from a Workers Custom Domain on `clint.broadhead.dev`, and everything runs with plain `npm`/`npx`. The old `@cloudflare/next-on-pages` (Pages, Edge runtime) is **deprecated** [next-on-pages README](https://github.com/cloudflare/next-on-pages), and Cloudflare's own docs now steer new projects to Workers over Pages entirely [Pages overview](https://developers.cloudflare.com/pages/). One nuance: Cloudflare's Next.js framework guide now headlines a new **vinext** (Vite-based) path as its default recommendation, but that targets **Next.js 16** and is in **beta**, so for a Next.js 15 app today the documented, production-orientated path remains the OpenNext adapter [Cloudflare Next.js guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/).

## Adapter and destination: Workers via `@opennextjs/cloudflare`

- **`@opennextjs/cloudflare`** deploys Next.js apps to **Cloudflare Workers** using the Node.js runtime from Next.js; it supports App Router, Route Handlers, SSR, SSG, ISR, Server Actions, PPR, and Turbopack [OpenNext Cloudflare docs](https://opennextjs.org/cloudflare).
  - Version support: "All minor and patch versions of Next.js 16 and the latest minors of Next.js 14 and 15 are supported"; Next.js 14 support drops in Q1 2026 [OpenNext — Supported Next.js versions](https://opennextjs.org/cloudflare/#supported-nextjs-versions). The published package pins peers `next >=15.5.24 <16 || >=16.3.3` and `wrangler ^4.125.0` [npm registry](https://www.npmjs.com/package/@opennextjs/cloudflare) — so Next.js 15.5.x is the exact supported 15-series line.
  - The adapter transforms `next build` output into a Worker (`wrangler.jsonc` points `main` at `.open-next/worker.js` with static assets in `.open-next/assets`) [OpenNext — Get Started](https://opennextjs.org/cloudflare/get-started).
- **`@cloudflare/next-on-pages` is deprecated.** Its README carries a warning banner: "The next-on-pages package is deprecated, if you want to deploy a Next.js application on Cloudflare, please use the OpenNext Cloudflare adapter instead" [next-on-pages README](https://github.com/cloudflare/next-on-pages). It was the Pages/Edge-runtime path — the Edge runtime intentionally constrains Node.js APIs and doesn't support all Next.js features [OpenNext — supported runtimes](https://opennextjs.org/cloudflare/#supported-nextjs-runtimes).
- **Workers, not Pages.** The Cloudflare Pages docs open with: "Workers supports most Pages use cases and offers a broader feature set. It is Cloudflare's primary platform for building applications. Start new projects with Workers" [Pages overview](https://developers.cloudflare.com/pages/). The Cloudflare Next.js framework guide routes all dynamic Next.js deployments to Workers; only static exports are pointed at Pages [Cloudflare Next.js guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/).
- **The newer "vinext" path (context, not our pick).** Cloudflare's framework guide (updated 2026-08-25) now says "Cloudflare recommends vinext as the default way to run Next.js applications on Cloudflare Workers", describing it as a Vite plugin that "reimplements the Next.js API surface" for **Next.js 16**, explicitly labeled "vinext is in beta" with a compatibility dashboard [Cloudflare Next.js guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/). OpenNext is still documented as the path "when you maintain an existing OpenNext application that cannot yet migrate to vinext because of a compatibility gap" [Cloudflare Next.js guide — other paths](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/#use-another-nextjs-deployment-path). For a greenfield Next.js 15 app we are closer to "existing app" than "Next 16 app"; adopting OpenNext now is the stable, documented route, and migration to vinext (which requires the Next 16 API surface) can happen later if desired.

## Route handlers and Node.js APIs — which runtime

- App Router **Route Handlers are supported** by `@opennextjs/cloudflare` [OpenNext — supported features](https://opennextjs.org/cloudflare/#supported-nextjs-features). Use the **Node.js "runtime"** from Next.js; the adapter explicitly says "your app should use the Node.js runtime, which is more fully featured, and allows you to use the Node.js APIs that are provided by the Cloudflare Workers runtime" [OpenNext — supported runtimes](https://opennextjs.org/cloudflare/#supported-nextjs-runtimes).
- Remove any `export const runtime = "edge"` — "The edge runtime is not supported yet with `@opennextjs/cloudflare`" [OpenNext — Get Started step 9](https://opennextjs.org/cloudflare/get-started).
- The app must run with the **`nodejs_compat` compatibility flag and a compatibility date of `2024-09-23` or later** for Next.js to work on Workers [OpenNext — Get Started step 3](https://opennextjs.org/cloudflare/get-started). On Workers, Node.js APIs are provided natively or via unenv polyfills when `nodejs_compat` is enabled — Buffer, `node:crypto`, `node:stream`, `node:http`, `process`, and others are listed as supported [Cloudflare Node.js compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/). (Newest nuance: compatibility dates `2026-08-04+` enable `nodejs_compat` behavior by default, without the flag [Cloudflare Node.js compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/).)
- Cloudflare bindings (KV, R2, secrets, etc.) are read in any server-side route — including route handlers — via `getCloudflareContext().env` from `@opennextjs/cloudflare` [OpenNext — Bindings](https://opennextjs.org/cloudflare/bindings).
- Streaming: Workers have **no duration limit** for HTTP requests — "As long as the client remains connected, the Worker can continue processing, making subrequests, and **streaming a response body**" [Cloudflare Workers limits — Duration](https://developers.cloudflare.com/workers/platform/limits/#duration), and there is **no enforced response body size limit** [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#request-and-response-limits). So a route handler streaming LLM tokens to the client is fine.

## Environment variables and secrets

- Plain (non-secret) vars go in the `vars` field of `wrangler.jsonc`; values of type Secret should **never** be put in `vars` [Cloudflare Secrets docs](https://developers.cloudflare.com/workers/configuration/secrets/).
- Secrets are a type of binding, set with `npx wrangler secret put <KEY>` (or via dashboard, or bulk with `wrangler deploy --secrets-file .env.production`) [Cloudflare Secrets docs](https://developers.cloudflare.com/workers/configuration/secrets/). Wrangler can validate required secrets at deploy time via the `secrets.required` configuration property [Cloudflare Secrets docs](https://developers.cloudflare.com/workers/configuration/secrets/).
- Access in app code: secrets/vars are read as `env.<KEY>` on the fetch handler, globally via `import { env } from "cloudflare:workers"`, or via **`process.env` when Node.js compatibility is enabled** — which is exactly how a Next.js/OpenNext app reads `process.env.OPENROUTER_API_KEY` in a route handler [Cloudflare Secrets docs](https://developers.cloudflare.com/workers/configuration/secrets/); alternatively `getCloudflareContext().env.<KEY>` [OpenNext — Bindings](https://opennextjs.org/cloudflare/bindings).
- Local development: put secrets in a `.dev.vars` file (dotenv syntax, gitignored); the OpenNext guide has you create `.dev.vars` with `NEXTJS_ENV=development` so Next.js `.env` files load in the expected mode [OpenNext — Get Started step 5](https://opennextjs.org/cloudflare/get-started), and `initOpenNextCloudflareForDev()` in `next.config.ts` wires up local bindings [OpenNext — Get Started step 12](https://opennextjs.org/cloudflare/get-started).
- Constraints: 64 vars/Worker on Free, 128 on Paid; each value ≤ 5 KB [Workers limits — Environment variables](https://developers.cloudflare.com/workers/platform/limits/#environment-variables). Fine for an OpenRouter key and a handful of access tokens.

## Custom hostname for `clint.broadhead.dev`

- **Use a Workers Custom Domain** (not a route): "Custom Domains point all paths of a domain or subdomain to your Worker… Cloudflare will create DNS records and issue necessary certificates on your behalf" [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/). A route is the wrong shape here — it matches a URL pattern on an existing proxied record and is aimed at overlaying a Worker on an existing origin, while a Custom Domain makes the Worker the origin for the whole hostname [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).
- Attach it either in the dashboard (Worker → Settings → Domains & Routes → Add → Custom Domain) or in `wrangler.jsonc` via `routes: [{ "pattern": "clint.broadhead.dev", "custom_domain": true }]` followed by `npx wrangler deploy` [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).
- **The existing proxied record matters.** The docs caution: "You cannot create a Custom Domain on a hostname with an existing **CNAME** DNS record" [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/). `clint.broadhead.dev` currently resolves to `2606:4700:…` (an existing proxied AAAA record, returning 530 because it has no origin). The documented migration procedure for a hostname that already has a record is: **delete the existing DNS record first, then add the Custom Domain** — the "Migrate from Routes" section walks exactly this: "Delete the CNAME record for `example.com`… Add custom domain… Run `npx wrangler deploy` to create the Custom Domain your Worker will run on" [Cloudflare Custom Domains — Migrate from Routes](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/#migrate-from-routes-via-wrangler). The 530 placeholder record has no origin behind it, so deleting it loses nothing; the Custom Domain then creates the DNS record and edge certificate automatically [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).
- Until the Custom Domain is attached, the Worker is reachable on its `*.workers.dev` subdomain, which is the default deploy target [Cloudflare Next.js guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/).
- Pages custom domains are moot for this app since the destination is Workers (see above).

## Runtime limits that could bite

- **CPU time** (network waits don't count): **10 ms/request on Workers Free; 5 min cap on Workers Paid with a 30 s default**. "Heavier workloads that handle authentication, server-side rendering, or parse large payloads typically use 10–20 ms." Exceeding it returns Error 1102 [Workers limits — CPU time](https://developers.cloudflare.com/workers/platform/limits/#cpu-time). Practical read: the free plan's 10 ms is tight for SSR-heavy Next.js; the chat app's route handler work is mostly awaiting OpenRouter, which is free of CPU-time cost, but plan on Workers Paid (or keep SSR light) if CPU errors appear. The default can be raised to 5 min via `limits.cpu_ms` in the Wrangler config [Workers limits — CPU time](https://developers.cloudflare.com/workers/platform/limits/#cpu-time).
- **Subrequests**: **50/request on Free; 10,000/request on Paid** (adjustable via `limits` config) [Workers limits — Subrequests](https://developers.cloudflare.com/workers/platform/limits/#subrequests). One OpenRouter call per chat turn is nowhere near the limit; even many chunked R2/KV reads fit comfortably on Paid.
- **Simultaneous open connections**: 6 per invocation waiting for response headers (fetch, KV, R2, etc.) — additional connections queue rather than fail [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#simultaneous-open-connections). Irrelevant for a single-upstream chat handler, worth knowing if batching fan-out later.
- **Streaming / duration**: no duration limit on HTTP requests and streaming response bodies is explicitly supported while the client stays connected [Workers limits — Duration](https://developers.cloudflare.com/workers/platform/limits/#duration); no enforced response body size limit [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#request-and-response-limits). Token streaming to the browser is fine.
- **Worker bundle size**: current limits page says **64 MiB uncompressed** on both plans, with **no compressed size limit — "Only the uncompressed bundle size counts"** [Workers limits — Worker size](https://developers.cloudflare.com/workers/platform/limits/#worker-size). ⚠️ Note a discrepancy: the OpenNext docs still say "The size limit of a Cloudflare Worker is 3 MiB on the Workers Free plan, and 10 MiB on the Workers Paid plan" and judge by gzip size [OpenNext — Note on Worker Size Limits](https://opennextjs.org/cloudflare/#note-on-worker-size-limits). That reflects the old compressed-size limit and looks **stale** relative to the current Workers limits page (updated Sep 5, 2026); a Next.js bundle at a few MiB gzipped is well under 64 MiB uncompressed either way, but treat the OpenNext page's numbers as outdated and check `wrangler deploy --dry-run` output, which prints both Total Upload (uncompressed) and gzip sizes [Workers limits — Worker size](https://developers.cloudflare.com/workers/platform/limits/#worker-size).
- **Memory**: 128 MB per isolate on every plan — matters only if buffering huge payloads; stream instead [Workers limits — Memory](https://developers.cloudflare.com/workers/platform/limits/#memory).
- **Static assets**: up to 20,000 files (Free) / 100,000 (Paid) per Worker version, 25 MiB per file — ample for a Next.js build [Workers limits — Account plan limits](https://developers.cloudflare.com/workers/platform/limits/#account-plan-limits).
- **Requests**: 100,000/day on Free; unlimited on Paid [Workers limits — Daily requests](https://developers.cloudflare.com/workers/platform/limits/#daily-requests).

## Toolchain: npm is sufficient

- Every documented flow uses npm: `npm create cloudflare@latest -- my-next-app --framework=next` to scaffold, `npm install @opennextjs/cloudflare@latest`, `npm install --save-dev wrangler@latest`, and `npm run deploy` = `opennextjs-cloudflare build && opennextjs-cloudflare deploy` [OpenNext — Get Started](https://opennextjs.org/cloudflare/get-started). Nothing in the docs requires pnpm, yarn, or bun, and all commands are exposed as plain package scripts, so npm 11 runs them.
- Wrangler ≥ 3.99.0 is required for Next.js apps via OpenNext [OpenNext — Get Started step 2](https://opennextjs.org/cloudflare/get-started); latest wrangler (4.135.0) declares `engines.node >=22`, satisfied by the installed node v24.18.0 [npm registry](https://www.npmjs.com/package/wrangler).
- The adapter's peer range (`next >=15.5.24 <16 || >=16.3.3`) is the one constraint to honor when scaffolding — pin Next.js 15.5.x [npm registry](https://www.npmjs.com/package/@opennextjs/cloudflare).

## Recommended deployment path (concrete)

1. Scaffold the Next.js 15.5.x app normally (plain `next` build; `npm` throughout).
2. Add `@opennextjs/cloudflare` + wrangler (dev), run `npx @opennextjs/cloudflare migrate` for automated setup (it generates `wrangler.jsonc`, `open-next.config.ts`, scripts; creates an R2 bucket for incremental cache if R2 is enabled) [OpenNext — Get Started](https://opennextjs.org/cloudflare/get-started).
3. Ensure `wrangler.jsonc` has `nodejs_compat` + compatibility date ≥ `2024-09-23`, `main: .open-next/worker.js`, `assets` binding `ASSETS`, and optionally the R2 cache binding [OpenNext — Get Started step 3](https://opennextjs.org/cloudflare/get-started).
4. Add `public/_headers` cache rule for `/_next/static/*` [OpenNext — Get Started step 7](https://opennextjs.org/cloudflare/get-started).
5. Keep route handlers on the default (Node.js) runtime; no `export const runtime = "edge"` [OpenNext — Get Started step 9](https://opennextjs.org/cloudflare/get-started).
6. Configure the OpenRouter API key and access tokens as secrets: `npx wrangler secret put OPENROUTER_API_KEY`, read via `process.env` / `getCloudflareContext().env` in route handlers; keep `.dev.vars` for local dev [Cloudflare Secrets](https://developers.cloudflare.com/workers/configuration/secrets/).
7. `npm run deploy` → serve from `*.workers.dev`, then delete the placeholder `clint.broadhead.dev` DNS record and attach `clint.broadhead.dev` as a Workers Custom Domain (`routes` with `custom_domain: true` in `wrangler.jsonc`, then `npx wrangler deploy`) [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).

## Open questions

- **R2 for the incremental cache**: enabling ISR/`'use cache'` caching wants an R2 bucket (`NEXT_INC_CACHE_R2_BUCKET`) [OpenNext — Get Started](https://opennextjs.org/cloudflare/get-started). For a single-document chat app with mostly dynamic routes this may be optional; decide when scaffolding.
- **Workers Free vs Paid**: the 10 ms/request CPU limit on Free is workable for a chat proxy but leaves little headroom for Next.js SSR; whether to start on Paid ($5/mo) depends on ticket 09's spend-ceiling decision.
- **vinext timing**: Cloudflare now headlines vinext for Next.js 16; it's beta and this app targets Next 15. If the project later upgrades to Next 16, re-evaluate migrating from OpenNext to vinext (and whether OpenNext's Next 15 support window keeps pace with Next.js upstream support).
- **Exact dashboard/API behavior when overriding the existing proxied record**: docs only explicitly cover the CNAME caution and the delete-then-add migration flow; the existing record on `clint.broadhead.dev` is AAAA, and the ticket owner should confirm in the dashboard whether Cloudflare offers to override it or requires manual deletion first (manual deletion is documented and safe here since the record has no origin).
